# Editorial checklist

Use this review after drafting or rewriting ECP documentation. The patterns below are editing signals, not proof that text was generated by AI. Fix the weak content behind a signal; do not only replace a flagged word.

Source: [Wikipedia: Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing). The source is descriptive and Wikipedia-specific in parts. This checklist adapts the relevant patterns to technical project documentation.

## Content

### Remove inflated importance

Delete claims that a routine decision is `pivotal`, `crucial`, `transformative`, a `testament`, or part of a wider trend unless the document gives evidence and the claim changes a decision.

Write the direct effect:

- Avoid: `The contract plays a pivotal role in enabling seamless collaboration.`
- Use: `Both lanes build against the same OpenAPI contract.`

### Remove shallow analysis

Do not add an `-ing` phrase that only interprets the previous fact.

- Avoid: `The frontend uses generated types, ensuring consistency across the platform.`
- Use: `The frontend uses generated types. CI fails when they differ from the contract.`

Keep cause and effect only when the project evidence supports it.

### Name the actor and relation

Replace vague association with the exact relationship.

- Avoid: `Redis is associated with rate limiting.`
- Use: `The API stores rate-limit counters in Redis.`

Replace vague authority such as `experts`, `industry practice`, `teams often`, or `it is widely accepted` with a named project source. Delete the claim if no source exists.

### Do not manufacture completeness

Do not add generic benefits, challenges, future prospects, best practices, or three-item lists to make a section look balanced. Record only known risks, decisions, actions, and owners.

Do not close a section with a broad summary that repeats its opening. End after the last useful fact.

## Words and sentences

### Prefer plain constructions

Use `is`, `has`, or an exact action verb instead of inflated substitutes.

| Avoid | Prefer |
|---|---|
| serves as | is |
| functions as | is; runs as |
| boasts; features | has; includes |
| leverages; utilizes | uses |
| facilitates | allows; supports |
| underscores; highlights | shows; or delete |
| aligns with | meets; matches |
| enhances | improves, with the measured effect |
| robust | name the failure it handles |
| seamless | name the handoff or remove the claim |
| comprehensive | state the covered scope |
| landscape; ecosystem | name the systems or teams |

These words are not banned when they are exact. Repeated use or use without evidence is the problem.

### Avoid staged contrast

Avoid `not only X, but also Y`, `not X, but Y`, and `rather than X` when a direct sentence works.

- Avoid: `The gate is not just a checklist; it is a runtime proof.`
- Use: `The gate requires runtime evidence.`

Use contrast only when the distinction itself is a project rule.

### Avoid automatic groups of three

Do not force claims or adjectives into groups of three. Include the exact number of items supported by the source.

### Control sentence load

- Aim for one main clause and one supporting clause.
- Split a sentence when it carries more than one condition, result, or exception.
- Keep exact technical noun phrases intact even when they are long.
- Prefer a repeated domain term over elegant variation.
- Remove throat-clearing such as `It is important to note that`, `In order to`, `In the context of`, and `As mentioned above`.

## Formatting

- Use bold only for scan targets such as a status or a required field. Do not bold a claim for drama.
- Avoid bullet lists shaped as `**Label:** explanation` when a plain list, paragraph, or real table is clearer.
- Avoid emoji and decorative separators.
- Use em dashes rarely. Prefer a period, colon, comma, or parentheses when the relation is clearer.
- Do not use a table for two facts that read faster as a sentence.
- Keep heading levels sequential. Do not add headings for one short paragraph.
- Do not leak chat text, placeholders, citation tokens, or writing-block markers into repository files.

## Project-specific review

Before finishing, verify:

- The text assumes readers know Scrum, DDD, CQRS, REST, OpenAPI, Kafka, Redis, Next.js, Spring, common security controls, and standard diagram notation.
- Any explanation of those subjects states an ECP-specific choice, limit, or exception.
- The same claim is not repeated in an index, overview, table, and closing paragraph.
- A link replaces duplicated detail when another file is authoritative.
- Counts such as operations, paths, stories, sprints, and ADR ranges still match the source.
- Normative and advisory statements remain distinct.
- Draft, accepted, blocked, and unverified states remain explicit.
- The final text contains no unsupported praise, prediction, or assurance.

## Final read

Read once as the target engineer or product owner:

1. Can any sentence be removed without losing a decision, constraint, action, or traceability fact? Remove it.
2. Can two adjacent sentences state the same point once? Merge them.
3. Does a simple word keep the same precision? Use it.
4. Did the edit change scope, certainty, or ownership? Restore the original meaning.
5. Does the prose sound like commentary about a document instead of the document itself? Rewrite it as a direct project statement.
